# 블로그 글쓰기 가이드

사실·변환 규칙과 frontmatter, `~` 금지 규칙은 프로젝트 `CLAUDE.md`가 기준이다. 이 문서는 **어떻게 읽히게 쓰는가**만 다룬다. 둘이 충돌하면 CLAUDE.md가 이긴다.

## 1. 쓰기 전에 정할 것

- **독자 한 명**을 정한다. 예: "Expo로 앱을 만드는 3년 차 개발자". 내가 중요하다고 생각하는 것보다 독자가 궁금해할 것을 쓴다.
- **한 문장 요지**를 정한다. 이 문장이 frontmatter `description`이 된다. 한 문장으로 안 나오면 아직 쓸 때가 아니다.
- **분량**: 읽는 시간 5분에서 10분. 넘치면 시리즈로 나눈다(기존 part1부터 part5 시리즈처럼).

## 2. 구조

1. **도입: 대상 시스템과 문제를 바로 밝힌다.** 무엇을(시스템·범위), 어떤 문제가 있었는지, 이 글이 무엇을 다루는지 두세 문단 안에 쓴다.
   - 소설식 장면 묘사("사용자가 링크를 누른다. … 문서는 어디에도 없다.")로 시작하지 않는다. 이 블로그는 기술 블로그다.
   - "요즘 ~가 화제다", 정의부터 늘어놓는 도입도 쓰지 않는다.
2. **본문: 문제 → 원인 → 대안 검토 → 선택 → 결과.** 원문에 없는 단계는 만들지 않는다(CLAUDE.md 서사 생성 금지).
   - **"택하지 않은 방식" 절을 둔다.** 원문에 검토했지만 택하지 않은 대안이 있으면 마무리 앞에 별도 H2로 모은다. 표(방식 | 택하지 않은 이유)가 읽기 좋다. 의사결정 과정이 드러나고 "X는 왜 안 썼나"라는 질문을 미리 막는다.
   - 이유는 지금 시점의 판단으로 쓴다. "SDK 58 때 재검토" 같은 향후 계획은 붙이지 않는다.
3. **마무리: 요약 반복 대신 남는 것 하나.** 핵심 판단이나 배운 점 중 원문에 있는 것만. 후속 과제·TODO·재검토 기준·검증 예정 같은 내부 작업 관리 항목은 원문에 있어도 블로그에 옮기지 않는다.

- H2 제목만 훑어도 흐름이 보여야 한다. "개요", "배경", "결론" 같은 빈 제목보다 내용을 담은 제목을 쓴다.
- 문단은 짧게(3문장에서 5문장). 한 문단에 한 가지 생각.

## 3. 문체

- **해라체 평서문**("~다", "~했다")으로 통일한다. 기존 포스트 문체다.
- 1인칭은 "나" 또는 "우리"(팀 작업일 때). 섞지 않는다.
- 추상적 설명 뒤에는 **구체 예시**를 붙인다: 실제 코드, 수치, 에러 메시지, 문제 목록 표.
- 의인화·스토리텔링 비유(택배 기사, 창구, 주머니 같은 것)를 쓰지 않는다. 원문에 비유가 있어도 기술 용어로 바꾼다. 소제목도 비유 대신 기술 내용으로 짓는다.
- "경고등", "위생", "보관함" 같은 은유 대신 기술 용어("재검토 기준", "데이터 격리", "대기 목적지")를 쓴다.
- 문장 길이를 섞는다. 짧은 문장은 강조로 쓴다.
- 능동태를 쓴다. "~되어진다", "~에 의해" 같은 이중 피동·번역투를 피한다.
- **사람을 주어로.** "이 라이브러리는 초기화를 수행한다"보다 "이 명령을 실행하면 초기화된다". 도구가 주어인 문장이 줄줄이 이어지지 않게 한다.
- 한 문장에 생각 하나. "~하게 되며, ~할 수 있다"로 길어지면 나눈다.
- 빈 한자어 동사를 뺀다. "삭제하는 작업을 수행한다" → "삭제한다"(수행·진행·실시·처리).
- 명사 나열을 동사로 푼다. "인증 처리 완료 후 접속 설정 진행" → "인증한 뒤 접속하도록 설정한다".
- 같은 종결어미가 세 번 이상 이어지면("~했다. ~했다. ~했다.") 어미를 바꾸거나 문장을 합친다.
- 변경 이력처럼 쓰지 않는다. 결과물을 설명할 때는 "~로 수정했다"가 아니라 현재 상태를 쓴다.

## 3-1. 용어·표기

- 같은 개념은 글 전체에서 한 단어로. 사용자/유저, 추가/첨부를 섞지 않는다.
- 약어는 처음에 한 번만 풀어 쓴다: `SSR(Server-Side Rendering)`, 괄호 앞은 붙인다. 그 뒤로는 약어만.
- 한영 병기는 처음 한 번만. "엔지니어링(Engineering)"을 반복하지 않는다.
- 제품·기술 이름은 공식 표기와 대소문자를 따른다(Kubernetes, GitHub, TypeScript).
- 외래어는 업계 관례를 따르고 한 번 고른 표기를 유지한다(프론트엔드). 합성 외래어는 붙여 쓴다(웹사이트, 데이터베이스).
- 숫자: 수치·날짜·측정값은 아라비아 숫자, 관용 표현(한두 번)만 한글. 단위·%는 붙이고(3개, 50%) 천 단위 쉼표(10,000). "1만"과 "10,000"을 섞지 않는다.
- 따옴표는 직선 따옴표(`"`)를 쓴다.

## 4. AI 티 제거 체크리스트

하나쯤은 괜찮다. 여러 개가 몰려 있으면 고친다.

| 패턴 | 예 | 고치는 법 |
|------|----|-----------|
| 빈 강조어 | 혁신적인, 획기적인, 핵심적인, 필수적인, 중요한 | 무엇이 왜 중요한지 사실로 쓴다 |
| 기계적 접속어 | 이처럼, 또한, 이를 통해, 이러한, 마침내, 결론적으로 | 지우고 읽어 본다. 대부분 없어도 된다 |
| 번역투 | ~에 대해, ~를 가지다, ~하는 것이 가능하다, ~로서의 역할을 한다 | "~이다", "~할 수 있다"로 줄인다 |
| 습관적 3개 나열 | "빠르고, 안전하고, 확장 가능한" | 실제로 있는 개수만 쓴다 |
| 대구 공식 | "단순히 A가 아니라 B다", "A뿐만 아니라 B도" | 평서문으로 쓴다 |
| 영어식 쉼표 | 주어 뒤, 접속사 앞의 쉼표 | 한국어 호흡대로 뺀다 |
| 대시 남발 | 문장 중간의 `—` 강조 | 제목 외에는 쉼표나 문장 분리로 |
| 장식 서식 | 리스트마다 이모지, 모든 항목 첫 단어 볼드 | 볼드는 문단당 최대 하나 |
| 공식 결말 | "앞으로가 기대된다", "도움이 되었길 바란다" | 지운다 |
| 과잉 완곡 | "~일 수도 있을 것 같다" | 원문 판단의 강도대로 쓴다 |
| 접속사 뒤 쉼표 | "또한, ", "따라서, " | 쉼표를 뺀다. 가장 강한 AI 신호다 |
| 메타 담화 | 앞에서 설명했듯이, 다음으로 살펴보면, 아시겠지만, 사실은 | 지운다 |
| 형식명사 종결 | ~것이다, ~라는 점이다, ~할 필요가 있다, -적·-성·-화 연쇄 | 동사로 끝낸다 |
| 돌려 말하기 | ~역할을 한다, ~로 기능한다, 가능합니다/제공됩니다 반복 | "~이다", "~한다"로 |
| 굵은 라벨 목록 | `**속도:** 빨라진다` | 문장으로 풀거나 표로 |
| 제목 되풀이 | H2 바로 아래 첫 문장이 제목을 다시 말함 | 첫 문장부터 내용 |
| 허수아비 반론 | "~라고 생각할 수 있다. 하지만…", 자문자답 | 주장만 쓴다 |
| 막연한 권위 | 전문가들은, 업계에서는 | 출처를 달거나 지운다 |
| 범위 확장 결말 | "개인에서 팀, 조직으로", 무조건 낙관, 양비론 | 원문의 결론만 |
| 챗봇 말투 | 물론입니다, 솔직히 말하면, 도움이 되셨으면 | 지운다 |

## 5. 기술 글 서식

- 코드 블록에는 언어를 지정한다(` ```ts `). 핵심 줄만 남기고 나머지는 `// ...`로 줄인다.
- 파일명·함수명·명령어는 백틱으로 감싼다.
- 비교는 표, 흐름은 번호 목록, 아키텍처는 다이어그램(Mermaid 또는 이미지).
- 외부 사례·자료를 인용하면 출처 링크를 단다.
- 링크 텍스트는 대상 문서의 제목이나 설명으로. "여기", "이 글", 맨 URL은 쓰지 않는다.
- 제목 수준을 건너뛰지 않는다(H2 다음 H4 금지). 본문 없이 제목 두 개를 연달아 두지 않는다. 제목에 링크를 넣지 않는다.
- 동작을 보여 줄 때는 스크린샷이나 GIF를 넣는다. 나중에 코드가 깨져도 기록이 남는다.
- 게시 후 오류를 발견하면 정오표를 따로 달지 않고 본문을 고친다.

## 6. 작업 절차

1. 참고 문서가 있으면 끝까지 읽고 핵심 판단·수치를 먼저 뽑아 둔다.
2. 독자, 한 문장 요지, H2 목차를 사용자에게 먼저 보여 준다(새 글일 때).
3. 초안 작성. 새 글은 `draft: true`로 둔다.
4. 퇴고: 4장 체크리스트 → CLAUDE.md "확인 절차" 3항목 대조.
5. `pnpm build`로 빌드 오류가 없는지 확인한다.

## 7. 제목·description

- 제목: 독자가 얻는 것이나 핵심 장면이 드러나게. 부제가 필요하면 `—`로 잇는다(기존 제목 형식).
- description: 1장의 한 문장 요지. 120자 이내.
- slug: 영어 kebab-case, 3단어에서 5단어.
- tags: 기존 태그를 먼저 재사용한다(`grep -h "^  - " src/data/blog/*.md | sort | uniq -c`).
